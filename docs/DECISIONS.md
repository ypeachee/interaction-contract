# Design Decisions

## 2026-11-20 — 使用 Quick / Full 两条路线

**决定：** 单核心流程使用 Quick；多界面、持久化、跨端或长期维护使用 Full。

**原因：** 同一套十章结构能保持一致，但小任务不应被迫写重型规格。  
**否决：** 只做一条“大而全”流程，容易让简单需求成本过高。  
**升级条件：** 出现第二个独立界面、持久化、权限、导入导出、跨端或不可逆操作。

## 2026-11-20 — 交互契约先于实现

**决定：** 契约未被用户确认前，不进入实现。

**原因：** 大部分返工不是代码不会写，而是用户意图、状态和验收没有对齐。  
**否决：** 先做原型再补规格；对探索性 spike 可以例外，但必须标记为一次性实验。

## 2026-11-20 — 验收测试使用 CSV

**决定：** 统一输出 `ACCEPTANCE_TESTS.csv`。

**原因：** 可被人类、表格工具和脚本共同读取；容易在后续会话中继续执行。  
**否决：** 只把验收标准写在 Markdown 列表里，无法稳定追踪状态与证据。
