# 案例研究提纲：从一句“我想要一个工作台”到可验收系统

## 标题候选

1. 《AI 编程真正难的不是写代码，是验收》
2. 《从一句“我想要一个工作台”到可用系统》
3. 《领域专家不需要会写代码，但必须会写验收》

## 要回答的核心问题

当用户不是专业程序员时，怎样把真实工作变成 AI 可以执行、自己又能验收的交互系统？

## 结构

### 1. 背景

- 用户身份与真实任务；
- 旧工作流：纸质、PDF、多个文件、手工记录；
- 为什么普通聊天/搜索不够。

### 2. 第一次失败或混乱

- 需求太模糊；
- 页面先做出来，但关键状态没定义；
- 进度丢失、导入失败、刷新后状态不一致；
- 只验证“能打开”，没有验证“能恢复”。

### 3. 引入交互契约

展示三个关键产物：

- 用户与核心任务链；
- P0 / 非目标；
- 状态矩阵；
- 验收测试 CSV。

### 4. 真实缺陷如何被抓住

选择 2 个具体案例：

- 刷新后进度丢失；
- 分组/筛选后选中项错误或首屏为空；
- 重复提交；
- 非法导入破坏原数据；
- APK 构建成功但未做真机验收。

每个案例写：

```text
预期 → 实际 → 证据 → 修复层 → 回归测试
```

### 5. 结果

记录可量化指标：

- 需求来回轮次；
- 首次实现的 P0 完成率；
- 验收发现缺陷数；
- 刷新/重开恢复成功率；
- 中断后续接所需时间；
- 用户完成任务所需时间（如有真实用户）。

### 6. 可迁移方法

总结成 5 条：

1. 先定义核心任务，不先画页面；
2. 每个 P0 必须覆盖空/加载/成功/错误/恢复；
3. 验收必须带证据；
4. 未知项必须显式保留；
5. 构建成功不等于真实可用。

### 7. 边界

- 单案例不能证明普适效果；
- 没有真实用户测试时，只能声明作者自测；
- 不公开版权内容、个人隐私和密钥；
- 不把 AI 生成的交互规格当成无需人工确认的最终决定。

## 证据清单

- 交互契约前后版本；
- 截图/录屏；
- 验收测试结果；
- bug 修复前后的证据；
- 用户引语（经授权并匿名化）；
- 时间和缺陷数量。
